# MicMask Link v1 传音协议规范

> 状态：v1（2026-11-28 定稿第一版）。实现：`app/src/main/kotlin/com/taocrypt/micmask/link/MmLink*.kt`（纯 Kotlin，不依赖 Android），
> 电脑版（`desktop/`）构建时原样复制这几份源码编译，两端同一份代码。单测：`tools/linktest/`（kotlinc 独立运行）。
> MicYou 兼容协议（`MicYouWire.kt`、`LinkNet.kt`）保持原样，作为可选项继续提供。
>
> 2026-11-28 修订（2.1.1-alpha.13）：线格式**未变**（仍是 v1，新旧版本互通），只改实现行为：UDP 数据报上限 1200 字节、UDP 回退/保活/中途回退 TCP、全部网卡监听与地址展示、连接失败分类、按设备 ID 自动连接。见 §2.1、§6、§11。
>
> 2026-11-28 第二次修订（2.1.1-alpha.13，phone13）：线格式**仍未变**，帧与字段一个不改，只新增一个 CAPS 能力位并调整实现行为，旧版照样能连：
> - CAPS 新增能力位 `16 = CAP_PREF_RX`：编码改为「接收方偏好优先」（§5.1）；CAPS 允许会话中重发，用于同一条会话双向（§5.2）；
> - STATS.bufMs 含义写清（§5.3）；接收缓冲目标随抖动 / TCP / 断流自适应、漂移裁剪与 PLC（§7）；
> - 服务端不再要求 UDP 来源 IP = TCP 对端（修 EasyTier 等代理 TCP 时 UDP 永远不通，§6）；心跳超时随 RTT 自适应；TCP 发送队列积压丢旧音频（§7.1）；
> - 二维码配对（§12）；Tailscale 插件预留接口 `TsBridge`（§13）。

## 1. 目标与范围

- 局域网内手机 ↔ 电脑、手机 ↔ 手机互传实时音频，**双向**：一条会话里任一端都可以发也可以收（由 CAPS 声明）。
- 默认加密：不知道配对码的人连不上，被动监听也听不到。
- 48 kHz 单声道，10 ms 一帧（480 样本），与手机端 shell 主循环节拍一致。
- 编码可选：Opus（默认）或 PCM s16le。

## 2. 角色、端口与发现

| 项 | 值 |
|---|---|
| 监听方（服务端） | 打开「接收」的一端：显示 6 位配对码 |
| 发起方（客户端） | 选设备并输入配对码的一端 |
| 端口 | TCP 与 UDP 同号，默认 **47310** |
| mDNS 服务类型 | `_micmask._tcp`（实例名 = 设备名，如 `MicMask-<机型>`、`MicMask-PC-<主机名>`） |
| mDNS TXT | `app=micmask`、`v=<协议最高版本>`、`plat=android|windows`、`id=<设备 ID 前 4 字节十六进制>` |
| USB | 电脑执行 `adb reverse tcp:47310 tcp:47310`，手机连 `127.0.0.1`；adb reverse 只转 TCP，此时音频走 TCP（见 §6） |

监听方 TCP 与 UDP 都绑定 **0.0.0.0（双栈通配地址）**，所有网卡都能连：Wi-Fi、热点、USB 网卡，以及 VPN / 虚拟网卡（EasyTier、Tailscale、ZeroTier 等）。

### 2.1 跨网段 / 组网（EasyTier、Tailscale、ZeroTier）

- mDNS 只在同一链路内有效，跨网段或经隧道时搜不到，需要**手填对方 IP**（手机接收页「本机地址」列出全部网卡地址并标注接口名与类型，VPN 地址单独标出；Android 上第三方 VPN 都叫 `tunN`，按网段推断：`100.64.0.0/10` → Tailscale，`10.144.144.0/24` → EasyTier 默认段，`zt*` → ZeroTier）。
- 手填地址格式：`host`、`host:port`、`[IPv6]:port`、裸 IPv6。
- 隧道地址（非 RFC 1918 私网、CGNAT、EasyTier 默认段、主机名）连接超时放宽到 6 s（局域网 3 s），握手超时 8 s（局域网 5 s）——中继/打洞路径首包可能要几秒。
- 常见失败原因（推断，未实测）：Windows 把虚拟网卡归为「公用网络」，防火墙不放行入站 TCP/UDP 47310（表现为连接超时）。

同一时间一个监听方只服务一条会话；新会话握手成功后接管旧会话（旧会话收到 BYE「被新连接接管」）。

## 3. TCP 帧

```
帧 = u16 BE 长度 L（= 1 + 内容长度，≤ 65535）| u8 类型 | 内容（L−1 字节）
```

| 类型 | 名称 | 方向 | 内容 |
|---|---|---|---|
| 0x01 | HELLO | 双方各一次 | 见 §4.1（明文） |
| 0x02 | PAKE | 双方各一次 | SPAKE2 消息：P-256 非压缩点 65 字节（明文） |
| 0x03 | CONFIRM | 双方各一次 | HMAC-SHA256 确认值 32 字节（明文） |
| 0x10 | SEALED | 握手后 | `u64 BE 计数 | AES-GCM(内层消息)‖tag16`，AAD = 类型字节 0x10 |
| 0x7F | ERROR | 任一时刻 | `u8 错误码 | u8 长度 | UTF-8 说明`（明文，发完即断开） |

错误码：1 = 版本不兼容，2 = 配对码不对，3 = 忙/被锁定（配对码错太多），4 = 协议错误。

## 4. 握手

```
客户端 A                                   服务端 B
HELLO(a) ───────────────────────────────▶
          ◀─────────────────────────────── HELLO(b, connId)
PAKE(pA) ───────────────────────────────▶
          ◀─────────────────────────────── PAKE(pB)
CONFIRM(cA) ────────────────────────────▶  校验 cA；错 → ERROR(2)
          ◀─────────────────────────────── CONFIRM(cB)
校验 cB；之后双方只发 SEALED
SEALED{CAPS} ◀──────────────────────────▶ SEALED{CAPS}
```

### 4.1 HELLO 与版本协商

```
HELLO = "MMLK"(4) | minVer u8 | maxVer u8 | deviceId(16) | name(u8 长度 + UTF-8) | platform(u8 长度 + UTF-8)
      | nonce(16, 随机) | connId u32（服务端分配，非 0；客户端填 0）| needCode u8（v1 恒为 1）
```

- 协商版本 = `min(双方 maxVer)`，若小于 `max(双方 minVer)` 则不兼容 → ERROR(1)。v1 时 min = max = 1。
- 将来的 v2 可以把 maxVer 提到 2 而 minVer 保持 1，老客户端照样能连（按 v1 跑）。
- `deviceId`：每台设备首次运行随机生成并保存（手机 prefs `link_dev_id`，电脑 `%APPDATA%\MicMask\desktop.properties`）。

### 4.2 SPAKE2 配对（RFC 9382）

- 套件：**P256-SHA256-HKDF-HMAC**；M、N 为 RFC 9382 §6 给出的 P-256 点；h = 1。
- A = 客户端、B = 服务端；身份 idA / idB = 双方 deviceId（16 字节）。
- 口令 w：`w = OS2IP(HKDF-SHA256(ikm = 6 位配对码 ASCII, salt = "MicMask Link v1 pairing", info = "w", L = 64)) mod n`。
  （RFC 9382 允许自选 MHF；口令只有约 20 bit，慢哈希意义不大，取 64 字节再模 n 以消除偏差。）
- `pA = x·G + w·M`，`pB = y·G + w·N`；`K = h·x·(pB − w·N) = h·y·(pA − w·M)`。
- `TT = len(idA)‖idA‖len(idB)‖idB‖len(pA)‖pA‖len(pB)‖pB‖len(K)‖K‖len(w)‖w`（len 为 8 字节小端，w 为 32 字节大端）。
- `Ke‖Ka = SHA-256(TT)`；`KcA‖KcB = HKDF(Ka, salt = 空, info = "ConfirmationKeys"‖"MicMask Link v1", L = 32)`；
  `cA = HMAC(KcA, TT)`，`cB = HMAC(KcB, TT)`。
- 实现已用 RFC 9382 附录 B 第一组测试向量逐项校验（pA、pB、K、Ke、cA、cB，见 `tools/linktest`）。

安全性：被动监听拿不到 Ke；主动攻击者每次连接只能验证一个猜测（10⁻⁶）。服务端配对码**连续错 5 次锁 60 秒**（ERROR 3），限制在线猜码速度。
配对码保存在接收端，可在页面上「换一个」；发送端按设备名记住上次成功的配对码，下次自动填。

### 4.3 会话密钥

```
OKM = HKDF-SHA256(ikm = Ke, salt = nonceA‖nonceB, info = "MicMask Link v1 keys", L = 64)
c2s 控制 = OKM[0:16]   s2c 控制 = OKM[16:32]   c2s 音频 = OKM[32:48]   s2c 音频 = OKM[48:64]
```

全部 AES-128-GCM，nonce = `00 00 00 00 ‖ 64 位计数（大端）`。每把密钥只在一个方向、一个通道上用，计数单调递增、不复用。
接收方用 64 包滑动窗口防重放（控制按 SEALED 计数，UDP 按 pn）。

## 5. 内层消息（SEALED 里）

| 类型 | 名称 | 内容 |
|---|---|---|
| 0x20 | CAPS | `flags u32 | 偏好编码 u8 | Opus 码率 u32 | 帧样本数 u16（=480）` |
| 0x21 | PING | `u64 发送时刻毫秒` |
| 0x22 | PONG | 原样回 PING 的时刻 → 算 RTT |
| 0x23 | STATS | `RTT u16 | 抖动 f32 毫秒 | 丢包率 f32 | 接收缓冲 u16 毫秒 | 延迟估计 u16 毫秒`（收音频的一端每秒发） |
| 0x24 | BYE | `u8 长度 + UTF-8 原因` |
| 0x25 | AUDIO | 音频走 TCP 时：`seq u32 | ts u32 | codec u8 | flags u8 | 样本数 u16 | 数据` |
| 0x26 | UDP_OK | 客户端收到 UDP 探测回应后发，告诉服务端「UDP 双向已通」 |

CAPS flags：`1 = 本端会发音频`、`2 = 本端想收音频`、`4 = 支持 Opus`、`8 = 支持 PCM`（v1 两端都必须支持 PCM）、`16 = CAP_PREF_RX`（本端的「偏好编码」也是接收偏好，2.1.1-alpha.13 起新版恒置位）。
对方没声明「想收」时，发送方不发音频。未知内层消息类型、未知能力位一律忽略（向前兼容）。

### 5.1 发送编码：接收方偏好优先

实现：`MmCaps.pickCodec(sender, receiver, followReceiver)`。

| 情况 | 发送编码 |
|---|---|
| 任一方不支持 Opus | PCM |
| 发送方「跟随」（`MmLinkConfig.followPeerCodec = true`，默认）且接收方带 `CAP_PREF_RX` | 接收方的偏好编码 |
| 发送方「固定编码」（`followPeerCodec = false`），或接收方是旧版（没有 `CAP_PREF_RX`） | 发送方自己的偏好编码（v1 原规则） |

- 兼容：旧版发送方不认识 `CAP_PREF_RX`，照旧按自己的偏好发；接收端两种编码都能解，所以任意新旧组合都能出声。
- 会话中改编码：`MmSession.setTxCodec(codec)`（公开方法；对方不支持 Opus 时只能 PCM）。电脑端不再需要用反射改 `txCodec`。
- 手机端「高级 › 编码偏好」= 本机的 preferCodec：本机接收时告诉对方按它发；本机发送时默认跟随接收方。

### 5.2 同一条会话双向（CAPS 可重发）

- 任一端可以在会话中再发一次 CAPS（`MmSession.updateIntent(intent)`），对端以最后一次为准（旧版本来就是收到 CAPS 就更新 `peerCaps`，兼容）。
- 用法：手机发送连接建立时若「接收」也开着，CAPS 同时声明 `发 + 收`；之后开关「接收」会重发 CAPS。对端（电脑）若也想发给手机，**可以直接在这条会话上发**，不必再反向建一条连接。
- 接收方同时从两条会话收到音频时（对方既连了本机「接收」，又在本机的发送连接上回传），只用正在出声的一路（300 ms 没新包才切换），不叠加。
- 手机音源规则（防回环）：接收注入进行中时，发送取注入服务录到的**真麦**（不是注入前输出，否则会把收到的声音发回去）；自己的变声在运行时取注入前输出；都没开时 App 自己录原始麦克风。普通模式外放播放时，扬声器声音会被麦克风录到（回声），界面提示戴耳机。

### 5.3 STATS.bufMs 的含义

- `bufMs` = **接收端本地还没播放 / 注入的音频量**（毫秒）：抖动缓冲 + 本端输出队列（手机注入时为注入服务的输出环形缓冲，外放时为播放缓冲）；不含网络在途数据与声卡硬件缓冲。
- 2.1.1-alpha.13 起取**最近 1 秒的最低水位（谷底）**，不是瞬时值：瞬时值随包到达锯齿跳动，谷底才反映「多攒了多少」（漂移 / 积压）。旧版是采样瞬间的值。
- 0 = 还没出声或测不到。`latencyMs` = bufMs + RTT/2 + 10（估计值）。
- 发送端只应看 bufMs 的**相对变化**判断漂移（例如比本会话见过的最低值高出很多），不要和固定阈值比；接收端自己会裁剪（§7），发送端的追帧只是辅助。

## 6. UDP

```
头（明文，作 AAD）= "MA"(2) | ver u8（=1）| 类型 u8 | connId u32 | pn u32（每方向递增，作 GCM 计数）
音频（类型 1）    = 头 | seq u32 | ts u32 | codec u8 | flags u8 | 样本数 u16 | AES-GCM(编码数据)‖tag16      （AAD = 前 24 字节）
探测（类型 2）/ 回应（类型 3）= 头 | AES-GCM(u64 发送时刻毫秒)‖tag16
```

- 音频用「音频」密钥（方向同上）；PCM 10 ms 一包 = 24 + 960 + 16 = 1000 字节，Opus 约 55 字节/包。
- **数据报总长上限 1200 字节**（含明文头、密文与 tag；`MmLink.MAX_UDP_DATAGRAM`）：IPv6 + UDP 头 48 字节后 ≤ 1280（Tailscale 的 MTU，也是 IPv6 最小 MTU），EasyTier / ZeroTier 隧道 MTU 更大。v1 现有帧都满足，无需切帧；将来若有超长帧，发送端改走 TCP 内层 AUDIO。
- 音频从握手完成起就先走 TCP 内层 AUDIO，UDP 打通后才切过去，所以 UDP 不通不会无声。
- 客户端探测节奏：握手后前 **1.5 s** 每 0.5 s 发一次探测；1.5 s 内没回应即判定「UDP 暂不通」（日志说明，音频继续走 TCP），之后每 2 s 低频探测，通了自动切 UDP。
- 收到回应后发 TCP 内层 UDP_OK，双方音频改走 UDP；之后客户端每 1 s 发一次保活探测。连续 **3.5 s** 没有回应（隧道切换、NAT 映射过期）→ 客户端音频切回 TCP；回应恢复 → 再切回 UDP 并重发 UDP_OK。
- 服务端：UDP_OK 之后若已收到 ≥ 2 次保活探测（说明对端是会保活的新版本），连续 3.5 s 没收到探测即把本端发往客户端的音频切回 TCP；再收到 UDP_OK 时切回 UDP。老版本客户端打通后不再探测，服务端不据此判断，行为与旧版一致。
- 服务端接受**认证通过**（connId 匹配 + AES-GCM 校验 + 重放窗口）的数据报，并以最近一个认证通过的来源地址作为回发地址（适应 NAT/端口变化）。
  2.1.1-alpha.13 起**不再要求来源 IP = TCP 对端**：实测（电脑端日志，EasyTier 10.126.126.x）电脑接收时握手显示对端是 `10.126.126.1`——正是电脑自己的 EasyTier 地址，说明 EasyTier 在电脑侧代理了 TCP（来源被换成本机地址），而 UDP 来源仍是手机 `10.126.126.5`，旧规则把手机的 UDP 探测全部丢弃，表现为「UDP 始终不通、全程走 TCP」（推断，依据是握手日志里的对端地址；Tailscale userspace / 各种端口转发也会这样）。安全性不变：伪造数据报过不了 GCM 认证。
  首次收到来源与 TCP 对端不同的探测时写日志说明。客户端「UDP 不通」日志里附带已发 / 已收探测数与目标地址，便于区分「发不出去」「对方没回」「回包被防火墙挡」。
- 探测包 36 字节、Opus 帧约 60–160 字节、PCM 1000 字节，都低于 EasyTier 默认 MTU（1380）与 Tailscale（1280），MTU 不是 UDP 不通的原因（推断）。仍不通时最常见的是电脑防火墙没放行 UDP 47310 入站（Windows 把虚拟网卡归为「公用网络」）。
- UDP 不通（防火墙、AP 隔离、USB adb reverse）时音频走 TCP 内层 AUDIO，功能不变、抗抖动差一些。
- `seq`：音频帧序号（与 pn 分开，探测包不占 seq）；`ts`：发送端 48 kHz 样本计数，接收端用来算抖动。

## 7. 接收处理

- 重排：`SeqReorder`（与 MicYou 兼容路径同一份）：缺口等 3 个包（30 ms）再判丢；早于期望的丢弃；序号大跳当对端重启。
- 丢包补偿：Opus 用缺口后第一包的**带内 FEC** 恢复最后一帧，更早的用解码器 **PLC**，最多补 5 帧；PCM 直接跳过（由缓冲处理）。
- 抖动：`JitterMeter`（RFC 3550 风格）。
- 缓冲目标水位（`MmBufTarget`，两端共用的控制律，2.1.1-alpha.13）：
  - UDP：clamp(2.5 × 抖动 + 30, 下限, 上限)；手机取 60–140 ms；
  - TCP（UDP 不通、USB、隧道）：clamp(3 × 抖动 + RTT, 下限, 上限)，手机 100–200 ms——TCP 丢一个段要等一次重传（约 1 个 RTT），后面的包才一起到，缓冲至少要盖住一次重传；
  - 断流补偿：每次断流 +15 ms（最多 +80），20 s 无断流后每 5 s 回落 5 ms；目标升高立即生效、降低每 5 s 最多 10 ms。
  - 手机注入路径：目标通过注入服务 `TX_LINK` 子命令 4 实时改 shell 侧预缓冲（20–400 ms）；外放路径直接设到播放缓冲。
- 漂移裁剪（`MmDriftCtl`）：每 2 s 结算一次缓冲水位窗口——最低水位 > 目标 + 20 ms（持续超标，不是一次突发）→ 计划丢 (最低水位 − 目标)/2（每窗口 ≤ 40 ms）；
  最高水位 < 目标且最低水位 < 目标 − 30 ms（持续偏低）→ 计划补 (目标 − 最低水位)/2（10–40 ms）。动作只在**低能量 10 ms 帧**（峰值 < −40 dBFS）上执行；
  1.5 s 内一直找不到低能量帧才强制执行（丢：2 ms 交叉淡化；补：注入路径重复当前帧、外放路径补镜像衰减 PLC）。手机注入路径在推给注入服务前执行（注入服务自己的「谷底 > 预缓冲 + 30 ms 就裁」作为兜底仍保留）。
- 播放缓冲（`MmPlayout`，手机外放用，电脑端可直接复用）：攒够目标才出声并 2 ms 淡入；按上面的漂移裁剪丢 / 插；断流时在已有尾部之后补 10 ms「镜像衰减」PLC（与上一个样本连续、线性衰减到 0，避免硬切爆音），然后静音并重新预缓冲；硬上限 500 ms。
- 心跳：双方每秒 PING；超时 = max(5 s, 8 × 最近 30 s 最大 RTT)，音频走 TCP 时至少 10 s，上限 20 s（`MmSession.heartbeatFor`）。收到认证通过的 UDP 数据报也算对方活着。
  实测日志里 RTT 偶发 913 ms / 8073 ms（隧道上 TCP 重传）导致 5 s 心跳误断；断线后手机发送端照常按 1–30 s 退避自动重连。

### 7.1 TCP 发送队列（实现细节）

- 所有 TCP 帧先进发送队列，由写线程按顺序写 socket（SEALED 计数顺序因此不变）；调用方（音频线程）不再因为 TCP 卡住而阻塞。
- 队列里的音频超过 20 帧（200 ms）时丢最旧的音频帧（控制消息不丢）。被丢帧只在 SEALED 计数上留下空洞，接收端 64 包滑动窗口照常接受；接收端按 seq 缺口走 FEC/PLC。
- 链路恢复后不会把卡住期间积压的几秒音频一股脑送过去变成延迟。

## 8. 编码参数

- Opus：Concentus 1.0.2（libopus 纯 Java 移植，BSD-3-Clause），48 kHz 单声道、10 ms、VOIP、默认 48 kbps 目标（实测约 44 kbps）、带内 FEC 开、预期丢包 10 %、DTX 关、复杂度 5。
- PCM：s16le，960 字节/帧，约 800 kbps。适合 USB / 热点直连。

## 9. 与 MicYou 兼容协议的关系

- 手机「传音」页顶部「协议」可选：**MicMask 自有（默认）** / **兼容 MicYou**。兼容路径（TCP 8554 + UDP 8555、`_micyou._tcp`、明文、只 PCM）保持原样。
- 两种协议端口不同，互不干扰；同一时间只能用一种（切换前要先停止收发）。

## 10. 实现细节：连接失败分类与自动连接（不影响线格式）

- 客户端连接失败分两层：协议错误抛 `MmLinkException`（错误码 1–4，§3）；网络错误抛 `MmConnectFail(kind, stage)`，`stage` 0 = TCP 连接、1 = 握手，`kind`：
  超时（1）/ 被拒绝（2）/ 无法到达或主机名解析失败（3）/ TCP 已连上但对方不回握手（4）/ 握手中被断开（5）/ 其他（9）。`message` 是给人看的中文说明，日志另记阶段与原始异常。
- 设备身份 = HELLO 里的 `deviceId`（16 字节）。mDNS TXT 的 `id` 是它的前 4 字节十六进制，用来在地址变化后认出已保存设备。
- 手机端「自动连接」（默认开）：打开 App 时恢复接收（若用户上次没手动关）、依次尝试最近成功的已保存接收端（最多 3 台，局域网连接超时 1.5 s / 隧道 4 s），同时 mDNS 搜 20 秒，按 `id` 认出换了地址的设备并连上；
  发送中断线后按 1、2、4、8、15、30 秒退避重连（连接维持 30 s 以上才重置退避；配对码错、版本不符、对方主动停止或被别的设备接管时不重连）。接收端是监听方，本来就一直在等，断线后发送端重连即可；端口被占用时 5/10/20/30 秒退避重开。

## 12. 二维码配对（2.1.1-alpha.13）

- 接收端「传音」页在打开「接收」后显示二维码，内容：
  `micmask://link?h=<地址,…>&p=<端口>&c=<配对码>&id=<设备 ID 32 位十六进制>&n=<设备名>`，值做 URL 编码（UTF-8）。
  `h` 为本机全部网卡地址（与「本机地址」列表一致：局域网、热点、USB、VPN、IPv6；Tailscale 插件启用后含 tailnet 地址）。实现：`MmPairUri`（纯 Kotlin，两端共用）。
- 发送端点「扫码」：按需申请相机权限（拒绝 → 提示手填）；扫到后按「与本机同 /24 > 私网局域网 > 隧道 / 公网 > IPv6」依次尝试（`MmNet.orderHosts`），连上即按设备 ID 保存（含配对码），之后自动连接照常工作。
- 二维码只是把「地址 + 配对码」搬到发送端，握手仍是 SPAKE2，安全性与手填配对码相同；二维码等同于配对码，不要公开截图。
- 生成：zxing core 3.5.3（纠错 M）；扫码界面：zxing-android-embedded 4.3.0（Camera1 预览，不引入 CameraX）。两者 Apache-2.0。

## 13. Tailscale 插件预留接口（2.1.1-alpha.13，未实现）

`TsBridge`（`MmLinkNet.kt`，纯 Kotlin，两端共用），默认 `TsBridge.None`（全空，不改变任何行为）；插件加载成功后设置 `TsBridge.current`：

| 方法 | 含义 | 接入点 |
|---|---|---|
| `enabled` | 插件是否在工作 | 下面各处都先判断 |
| `tailnetAddrs()` | 本机 tailnet 地址（100.64.0.0/10、fd7a:115c:a1e0::/48） | 并入 `MmNet.localAddrs()` → 「本机地址」与二维码 |
| `expose(port)` / `unexpose(port)` | 把监听端口（TCP + UDP 同号）暴露到 tailnet（userspace / tsnet 模式需要；内核 TUN 模式返回 true 即可） | `MmLinkServer.start/stop` |
| `route(host, port)` | 连 tailnet 地址时给出本地代理：TCP `tcpHost:tcpPort`，UDP `udpHost:udpPort`（null = 不转 UDP，音频走 TCP）；返回 null = 直接连 | `MmLinkClient.connect` |

插件下载、库加载与实现由插件子任务提供，最后集成；实现要求：方法快速返回、不抛异常、线程安全。
